# 01 架构与安全模型

## 分层架构

```text
小程序页面（pages/*）
      │
      ▼
Service 层（miniprogram/services/*）          ← 页面不直接操作数据库
      │
      ▼
API 封装（miniprogram/api/cloud.ts）          ← 统一错误处理
      │
      ▼
云函数（cloudfunctions/<name>/src/index.ts）  ← 薄入口，只取微信身份
      │
      ▼
共享业务逻辑（cloudfunctions/_shared/）       ← SpaceService 等
      │
      ▼
数据访问层（Repo 接口）                       ← CloudRepo（云数据库）/ MemoryRepo（测试）
      │
      ▼
微信云开发数据库（5 个集合，全部拒绝客户端直连）
```

## 身份与授权链（安全核心）

客户端**不能**决定“我是谁”。云函数从微信上下文取得 `OPENID`，后端按固定链路解析：

```text
OPENID（getWXContext，不可伪造）
  → UserIdentity（provider=wechat_miniprogram, providerUserId=OPENID）
  → User（业务用户，id 才是业务主键）
  → SpaceMember（spaceId + role）
  → 真实 Space
  → 执行业务
```

规则：

1. 业务主键是 `User.id`，**不用 OPENID 当业务用户 ID**；
2. 云函数接口不接受客户端传入的 `userId / spaceId / role`，这些值一律由后端解析；
3. `space-info` 只返回“当前用户所属”的空间，没有按 spaceId 查询的接口；
4. 角色（OWNER/MEMBER）从 `space_members.role` 读取，客户端传任何角色都无效；
5. 邀请码绑定必须同时通过：邀请码存在、未使用、未过期、空间未满、本人未属于其他空间。

## 数据库安全规则（默认拒绝）

5 个集合在云开发控制台全部配置为**客户端不可读写**（见 `docs/security-rules/collection-rules.json`），
只有云函数通过管理员权限访问数据库。这样即使有人绕过小程序直接调用数据库 API，也拿不到任何数据。

## 已知边界与应对（第一阶段如实说明）

- 两人同时“加入”同一空间存在极小并发窗口：先后写入成员时，数据库唯一索引
  `space_members(spaceId + userId)` 会拦截重复加入；先到者成功，后到者收到失败提示，不会出现三人空间。
- 首次登录并发时会先写 User 再写 UserIdentity；若同一 OPENID 并发首次登录，唯一索引
  `user_identities(provider + providerUserId)` 保证只保留一条，失败方可重试。
- 邀请码为 8 位随机码（去掉易混淆字符），明文仅存在于后端数据库（客户端不可直连），绑定后立即置空。
- 时间统一规则：业务判定（邀请码有效期等）全部使用服务器时间（UTC 时间戳），前端只负责展示。
