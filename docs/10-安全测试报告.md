# 10 安全测试报告（第八阶段）

对应 PRD §62/§96。测试方式：本地自动化攻击测试（78 项全部通过，其中本阶段新增 8 项安全矩阵）+ 真实云数据库 E2E（13 项）。

## 1. 安全设计基线

- 身份只来自微信云函数上下文 `getWXContext().OPENID`，客户端无法伪造 userId / OPENID。
- 所有业务空间 ID 一律由“身份 → User → SpaceMember → 真实 Space”推导，**不接受客户端传 spaceId**。
- 角色来自数据库 `space_members.role`，客户端传 role 一律忽略。
- 记录访问一律 `spaceId + recordId` 双重限定，伪造 recordId / 跨空间 recordId 均返回 NOT_FOUND。
- 回收站 / 管理 / 导出 / 重发邀请码：仅 OWNER；MEMBER 返回 FORBIDDEN。
- 数据库集合全部 ADMINONLY，客户端无法直连，只能走云函数。

## 2. 攻击测试矩阵（全部必须失败，实际全部通过）

## 3. 本阶段修复的漏洞

审计发现 3 个云函数缺少身份/空间校验，已全部修复并部署：

1. **restaurant-images（图片临时链接，高危）**：原来任何人传入任意 `cloud://` fileID 都能换取临时 URL，可能跨空间读取私人照片。
   修复：必须为空间成员，且只允许换取**本空间餐厅/旅行资料中登记的 fileID**（`_shared/imageAccess.ts`）。
2. **restaurant-ocr（OCR，中危）**：原来任意 fileID 都可下载并送 OCR。修复：必须为空间成员。
3. **restaurant-search（地点搜索，低危）**：原来未绑定用户也能调用消耗 LBS 配额。修复：必须为空间成员。

## 4. 已知边界（设计内）

- 双人之间互相可见全部业务数据（这是产品定义，不是漏洞）；导出也包含双方数据。
- 邀请码 8 位 32 字符集（约 10^12 组合），未做调用频率限制，暴力枚举实际不可行。
- 数据库 ACL 为 ADMINONLY，云函数是唯一访问通道；云函数代码即权限边界。
